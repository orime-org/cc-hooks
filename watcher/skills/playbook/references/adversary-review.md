# 核实对抗返回、修复、停下

收到任何对抗 workflow 结果、核实返回、写修复方案、写对抗或 workflow prompt 时读。

## 1. 零发现先验是否零执行

对抗 workflow 返回零发现时，先看执行统计：`agents_error > 0` 或 `agents_done < agent_count` 就是没跑成，修掉原因重跑，不当通过。

理由：agent 挂掉时结果同样是空的，读起来跟「攻完没洞」一样。

判定：这个 0 是攻出来的，还是没攻？

## 2. 先查工作树有没有被改

每轮对抗跑完、动手之前，先 `git status --short` 查有没有陌生改动，`git diff` 认清后复原。某条发现描述的行为跟实现对不上时，先怀疑它读到的是被改过的版本。

理由：对抗者验证时可能改了工作树没还原，同一轮其他对抗者读到的就是改坏的那一版。

判定：这一轮跑完，工作区还是提交时的样子吗？

## 3. 核完再报数

逐条核完之前，不出轮次表，不报任何条数；中途汇报只说已核几条、剩哪几条、剩下的怎么核。审查表那份报告和修完停下的那份报告，都带从第 1 轮到当前轮的完整轮次表。

理由：核了一半的数跟全部的数长得一样，而要不要再跑一轮，正取决于没核的那几条。

判定：要写下的这个数，背后每一条都判完成立与否了吗？

## 4. UI 类返回先看屏幕

核 UI 类返回，第一问是那个位置屏幕上显示的是什么。用户点下去，得到所显示元素该有的响应，就是对的；没有任何可点暗示的元素，用户不会去点。

理由：体验由用户看到并操作的东西决定，代码在那一层还叠了什么不改变它。

判定：那个位置显示的是什么？点下去得到的是它该有的响应吗？

## 5. 技术事实为真，框架另判

返回里挂的技术事实为真，不等于它套的框架或描述的路径为真。「若那样写就出 X」，先问有没有人会那样写；框架单独判。凭空造出的路径不进任何分类，当场删掉。

理由：核实了一条真事实，容易把整个框架一起接受，然后为一种不存在的写法设计方案。

判定：这条路径真的存在吗？谁会走到它？

## 6. 成立的返回按类修

成立的返回是一个现象。先归类；再数本次范围内的同类成员（改语义时列全触发入口和同类点位，测连续多个的情形）；再改成写不出来的形状（类型、结构、唯一出口）。修复表「改了什么」一栏写这一类怎么消掉。

理由：只改被报的那一行，同类其余成员下一轮再被咬出来，轮次不收敛。

判定：这一类在本次范围里还有几个成员？它还能不能再发生？

## 7. 改删之前先列它承担什么

改或删一行、一个函数、一个属性之前，先列出它现在承担哪几件事，逐件问改完之后还成立吗。删除代价最高，要答得出它当初挡的是什么。

理由：修复引入的问题多出自没数清的影响面，而那些信息通常就在正在编辑的几行和相邻组件里。

判定：这一行当初为什么在这儿？

## 8. 停下信号

出现任一就停修：同一机制或同一块代码连续两轮被咬出洞；本轮问题都出自上一轮修复；修正反复膨胀并撞上同一条已定规则；同一个操作第二次追加前置检查。停下后问它该不该存在、所在的层对不对、那条规则是否定错了，报我；确实要做，就做覆盖全部同类的统一机制。

理由：这些信号说明问题出在这块东西本身，再修只会接着长出新问题。

判定：这一块已经被咬过几轮？问题出自哪一轮的修复？

## 9. 未拍板或别层的代码整块撤掉

洞出自一块我没拍过板、或属于别层（运维、部署）的代码时，审查表里的彻底方案写「整块撤掉、记 todo」，不修它的洞。

理由：给不该存在的东西打补丁，每一轮都在反方向推进。

判定：这块东西我拍过板吗？它属于本次要解决的那件事吗？

## 10. 派 agent 的 prompt 分两栏

派 agent 或对抗者时，prompt 分两栏：我权衡过代价拍定的，标不可改，只核实施细节；当前未验证的假设和我顺口给的回答，点名让它重点攻。agent 给出的方向裁决，一律对照拍板记录、设计和代码二审。

理由：agent 只看 prompt 里的局部，会按自己的直觉推翻已定方向；顺口的回答锁进「不可改」，每一道对抗都攻不到它。

判定：这条前提，是我权衡代价后拍的，还是回答某个问题时顺口给的？
