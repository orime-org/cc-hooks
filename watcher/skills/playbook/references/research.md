# 调研、选型、取证

查业界做法、选第三方库、拿实测读数或状态当证据、跨仓操作之前读。

## 1. 用一手来源

业界做法读官方文档或源码原文，二手文章转述的数字只当线索。许可证、版本这类属性能直接问成品就问成品（包里的许可证文件、程序自报的版本和构建信息），元数据字段只当线索。

理由：二手转述和元数据都可能跟成品对不上，写进文档或合规声明就成了假陈述。

判定：要写下的这个属性，来源是成品本身，还是某个字段、某篇文章的说法？

## 2. 样本是做同一件事的产品

业界调研的样本是做同一件事的产品；提供该机制的库只能证明机制存在。每家都查到它挂在哪、实际表现是什么，停在行为名上不算查完。

理由：机制存在不等于同类产品都用它；只看行为名，会把「机制不同」读成「它不做」。

判定：查到的这几条，回答的是「这个机制存不存在」，还是「做这件事的产品各自怎么做」？

## 3. 选型先列候选表

选型第一步列候选表并做对比。要装的包是从某个完整实现拆出来的，那个完整实现必须上表评估。说「评估过、因 X 没选」之前，先回查设计文档里有没有那次评估；没有就说没评估过。

理由：只有一个候选的表等于没枚举，完整实现已解决的问题会被漏掉；事后找到的理由不是当时的理由。

判定：这个包是不是某个更完整的东西拆出来的？那个东西在候选表上吗？

## 4. 读数先确认被测对象的状态

拿观测读数（探针、日志、计数）当证据前，先确认被测对象当时处在哪个状态。

理由：同一个读数在不同状态下含义不同，状态没确认，读数证明不了结论。

判定：取这次读数时，被测对象处在哪个状态？是怎么确认的？

## 5. 会变的状态开口前重查

PR、CI、远端分支 head、进程存活、端口占用、后台任务这类分钟级会变的状态，汇报或据此行动前重查一次，几分钟前的输出不算数。代码内容、文件存在这类同一轮内不会自己变的，可以复用先前的结果。

理由：自己查过的结果也有保质期，「我查过」的底气会掩盖它已经过期。

判定：要说的这个状态，几分钟内会变吗？会就先重查。

## 6. 路径和工作目录

工作目录可能沿用上一条命令切过去的目录，也可能被重置。跨仓 git 一律 `git -C <绝对路径>`；凭「某东西存不存在」下结论时用绝对路径，或先确认当前目录。

理由：目录切走之后，相对路径查到的是另一处不存在的同名路径，那个「没有」跟真的没有看起来一样。

判定：这条命令作用在哪个仓、哪个目录？确认过吗？
