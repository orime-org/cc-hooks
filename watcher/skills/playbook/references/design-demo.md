# 设计、状态流转、demo 到实现

写设计文档、设计涉及状态流转、定方案和验收结果、把 demo 转成实现和收尾比对时读。

## 1. 状态机先有状态流转文档

某个事实有两种以上状态、且有两条以上路径能改它时，写代码前先有状态流转文档，内容是：状态全集；事件全集（用户动作、响应回来、失败、超时、离开都算）；状态×事件转移表，每一格都填，不可能发生的格写凭什么；不变量和每个状态的唯一写入点。每一格都指得出出处（源码行、官方文档、本轮实验）；指不出的标「推断」，并在对抗 prompt 里点名让对抗者优先查这几格。

理由：空着的格是没人定义过的路径，运行时照样会走到；填了却没有出处的格比空格更难发现。

判定：要写的东西有几种状态、几条路径能改它？表里每一格的出处在哪？

## 2. 现状段先写，每句挂证据

设计文档的「现状」段先写完，每句挂着本轮真跑过的检索或真读过的行，再写方案。己方旧文档（含上一个任务的定稿）只作线索；旧文档给的范围表对着任务目标重新推一遍，推不出的不抄。写「现在缺 X，所以做 Y」之前，先检索 X 在不在。

理由：旧文档过期了自己不会说；照抄会为已经正确的机制设计替代品，或把范围外的事扩进来，而对抗查不到这两种。

判定：这句现状来自本轮读到的代码，还是抄自一份文档？

## 3. 先定结果，再定做法

定方案时，把所有真实会出现的情况下的结果逐个说出来（各语言、有内容和空内容、最长和最短的数据、明暗主题），有一个不对，做法就是错的。「取最坏情况定死」不算解法，不是规格的尺寸跟着内容走。

理由：满足约束不等于做对；按最坏情况定死，其余每种情况都被将就成最坏那种的样子。

判定：要写下的这个数，是有人定过的规格，还是量出来的某一种情况？

## 4. 全称规则靠结构强制

写下「所有 X 都要 Y」时，同时决定靠什么结构强制它（唯一入口、类型、访问器），不靠数今天有几个 X。共享结构有几种读法，就给几个各自命名的出口。同一条规则在第二处被漏掉，就停下来改结构。规则的范围不按与本意无关的属性（导出与否、公共或私有）把同类切成两半。

理由：X 的数量会增长，清单不会跟着长；共用一个出口会把两种用途的冲突藏起来；按无关属性切开的规则会在边界上漂移。

判定：不做 Y 的 X，现在还写得出来吗？

## 5. demo 定逻辑，数值对齐 token

demo 定功能逻辑和结构：哪个元素在哪一行、哪一格空着、有几种状态各长什么样。具体数值（色值、字号、间距、圆角、控件尺寸）对齐产品既有 token；仓里没有的挡位按真实内容的需要定。数值差异按这条自己办，不问我；只有 demo 的功能逻辑有问题，才先改 demo 给我看。动效以真机效果为准，参考仓里已校准的同类实现。收尾跟 demo 逐项对功能和结构，不对像素。

理由：demo 里的像素没经过 token 校准，照抄会在产品里引入第二套数值。

判定：这个差异是功能逻辑，还是数值？

## 6. 有 demo 的改动实测结构项

有 demo 的改动做 UI 实际使用时，用真实渲染结果逐项量 demo 定下的结构项（对齐、哪一格空着、哪些元素在同一行）；数值项对齐项目既有 token，不对像素。取数方法写在项目 skill 里。

理由：代码里写了的样式不一定渲染得出来；看截图时脑子里是刚写的代码，不是 demo。

判定：demo 定下的每个结构项，都有一个实测值吗？
