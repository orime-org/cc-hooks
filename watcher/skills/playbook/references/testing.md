# 写测试与验证

写或核守卫类测试、定测试范围、做批量替换、挑受影响范围验证的 smoke/E2E、跑全量测试时读。

## 1. 守卫测试用删除来验

守卫、锁、lint 规则的测试只有一种验证法：故意删掉被测的那块，看测试红不红。

理由：读测试代码看不出它是否真在保护那块；测试的环境配置错了，整组照样全绿。

判定：删掉被测的那块之后，测试红了吗？

## 2. 数得清的分支必须测完

数得清的判断分支必须测完，说得清有几个却没做完是欠账。数不清的输入组合、时序、环境状态，靠对抗和真跑。

理由：测试覆盖全部行为在理论上做不到，这一点不能拿来给漏测可数的分支开脱。

判定：这件事是说不清一共有几个，还是说得清但没做完？

## 3. 机械替换只变被换的东西

机械替换（换组件、换 API、改名）只许变被换掉的那个东西：先找新东西「什么都不加」的挡位；原有参数逐字保留；验收时逐处把新旧写法并排比对。

理由：替换过程常要求填一个新参数，顺手按自己的判断填，就改了行为或外观。

判定：除了被换掉的那个词，新旧写法完全一致吗？

## 4. smoke/E2E 的两道门

受影响范围验证要跑某条 smoke/E2E，先过两道门：改动属于接口、契约、数据格式、IO、配置或界面；那条 spec 真有一步走到改动的那行，并且新旧代码在那一步的结果不同。说不出是哪一步，就不跑。

理由：走不到改动的用例花了时间，什么都证明不了；它红了还会被误拿去做归属判定。

判定：这条 spec 的哪一步走到改动的那行？新旧结果有什么不同？

## 5. 全量输出存档

全量跑测试时，把完整输出存成文件再检索；红了要说得出用例名。

理由：终端输出会被截断，红过的用例名事后查不回来。

判定：如果有一条红了，能说出它叫什么吗？
